# OCTera

Интеллектуальная медицинская AI-платформа для автоматического анализа оптической когерентной томографии (ОКТ) сетчатки глаза.

Платформа предназначена для помощи врачам-офтальмологам в диагностике заболеваний глаз путем анализа медицинских изображений с использованием современных технологий компьютерного зрения и глубокого обучения.

OCTera не заменяет врача, а выступает в роли интеллектуального ассистента, который за несколько секунд анализирует ОКТ-снимок, обнаруживает патологические изменения, оценивает вероятность различных заболеваний, выделяет проблемные области и формирует предварительное медицинское заключение.

## Текущий этап продукта

Реализованный MVP — **self-service сервис** по модели ChatGPT/Claude: любой человек сам регистрируется и загружает собственные ОКТ-снимки, без понятия "врач ведёт карточки пациентов". Монетизация в этой модели — будущие подписки (см. «Бизнес-модель» ниже).

Клиническая/B2B-модель (несколько пациентов на одного врача, история и динамика по пациенту, PACS-интеграции, роли в клинике) — описана в разделах ниже как долгосрочное направление, но пока не реализована в продукте; технически для неё уже есть задел (в БД учётная запись пользователя 1-в-1 связана с профилем пациента, откуда при необходимости можно вырастить полноценную многопользовательскую модель).

## Разработка

Репозиторий — монорепо из двух частей:

- `backend/` — FastAPI-сервис: REST API, аутентификация, хранение исследований, оркестрация AI-пайплайна (`app/services/pipeline.py`).
  - **Quality-check** (`app/services/quality_check.py`) — реальная статистика по загруженному изображению: разрешение, резкость (дисперсия Лапласиана), экспозиция.
  - **Сегментация** (`app/services/segmentation.py`) — реальный сигнал-процессинг по пикселям снимка: границы слоёв отслеживаются **по каждому столбцу скана отдельно** (одно кандидатное положение на A-scan, привязка к ближайшему пику у соседнего столбца для непрерывности), а не одной усреднённой по всей ширине линией — на реальном изогнутом (не идеально плоском) снимке сетчатки, где глубина плывёт от столбца к столбцу, единая усреднённая по ширине линия давала бессмысленную, «размазанную» границу. Итоговая картинка — это сам снимок с закрашенными полупрозрачным цветом слоями и подписанной легендой (а не отдельная карта градиентов, которая ничего не подписывала и не показывала). Толщина слоёв в отчёте усредняется по всем столбцам. Не обучаемая модель и не per-pixel сегментация — честная эвристика на реальных данных снимка, а не случайные числа. Пересчёт в микроны использует условный коэффициент (нет калибровки скана) — абсолютные значения толщины иллюстративные. Точка, куда подключается обученная U-Net/nnU-Net при появлении размеченного датасета.
  - **Карта патологий** (та же `segmentation.py`) — алгоритмически находит гипорефлективные (тёмные) локализованные зоны внутри слоёв сетчатки — классический прокси для жидкости/кист/отслойки на ОКТ (они оптически "пустые", т.е. тёмные). Область поиска (верх/низ сетчатки на каждом столбце) определяется отдельным, более грубым и устойчивым детектором «где вообще есть ткань» (`_tissue_extent`), не тем же самым мелким послойным трекингом, что рисует карту слоёв выше — крупная патология (например, большая кистозная полость) может сбить с толку потонкий послойный трекинг именно в области находки, но грубая оценка «где ткань» остаётся надёжной и там. Это простой heuristic (локальный порог по яркости + фильтр по форме пятна), **не диагноз и не классификатор типа находки** — для точного разделения "киста vs жидкость vs артефакт" нужна модель, обученная на попиксельной разметке, которой пока нет. В интерфейсе и в тексте заключения явно помечено как "требует проверки врачом".
  - **Диагностика** (`app/services/diagnosis.py`) — реально обученный классификатор из `app/ml/` (см. ниже).
  - **Генератор заключения** (`app/services/report_generator.py`) — шаблонная сборка текста из структурированных находок, включая предупреждение при низкой уверенности модели (`LOW_CONFIDENCE_THRESHOLD`); описан как точка для подключения LLM (например, через Ollama — см. обсуждение ниже), но сама LLM пока не подключена (её веса тоже нужно откуда-то скачать, а публичные реестры моделей недоступны из этой песочницы).
- `frontend/` — личный кабинет на Next.js (App Router, TypeScript): вход/регистрация, прямая загрузка ОКТ-снимка, список своих исследований, страница результата (снимок, карта, толщина слоёв, вероятности диагнозов, текст заключения). Каждый пользователь видит только свои исследования (проверка владения на бэкенде, см. `app/api/deps.py:get_current_patient`).

### ML-классификатор диагнозов (`backend/app/ml/`)

Модель обучена на **реальных ОКТ-снимках пациентов**, а не на синтетике. Датасет: [OCT-AND-EYE-FUNDUS-DATASET](https://github.com/Traslational-Visual-Health-Laboratory/OCT-AND-EYE-FUNDUS-DATASET) (Hughes Cano, Olivares Pinto & Thébault; CONACYT/UNAM/IMO/APEC/INDEREB) — 1113 ОКТ-снимков с диагнозом диабетического макулярного отёка (DME), установленным врачами-офтальмологами. Классификация бинарная: `NORMAL` / `DME` — датасет не размечает другие патологии (CNV, друзы и т.п.), поэтому модель пока предсказывает только их.

`app/ml/train.py` подбирает лучший классификатор кросс-валидацией (сбалансированная точность, т.к. DME — миноритарный класс: 167 из 1113) среди нескольких кандидатов (MLP разных размеров, RandomForest, SVM с `class_weight="balanced"`, SVM после PCA(30) — см. round 11 — каждый обёрнут в `StandardScaler`). Признаки (`app/ml/features.py`): **HOG** (гистограммы ориентированных градиентов, 64×64) — они улавливают слоистую текстуру ОКТ гораздо лучше сырых пикселей — плюс доменные признаки, производные от того же сигнал-анализа, что и сегментация (протяжённость/толщина сетчаточной полосы, доля гипорефлективных зон = жидкость). Переход с сырых пикселей на HOG измеренно снизил долю ложных тревог по DME почти вдвое (см. историю коммитов).

**Текущие метрики** (см. полностью в `app/ml/artifacts/metrics.json`; пересчитывались несколько раз — round 10 исправил утечку по пациентам, round 11 сменил модель, round 14 нашёл ещё одну утечку, round 15 добавил усреднение по сидам, round 23 добавил аугментацию поворотом, round 27 исправил число компонент PCA и сам процесс отбора модели, см. ниже): на конкретном воспроизводимом чекпоинте (`random_state=42`, тот самый, что реально сохранён и используется в проде — `svm_rbf_pca75`, отобран автоматически через CV после исправления round 27) — test accuracy 93.6%, для класса DME precision 0.77 / recall 0.90 (дефолтный 50%-порог) либо precision 0.72 / recall **0.93** на CV-подобранном чувствительном скрининговом пороге (`DME_SCREENING_THRESHOLD` = 0.123, читается из `metrics.json` автоматически, а не хардкодится). Поле `multi_seed_evaluation` в `metrics.json` (test accuracy 94.2% ±1.3 п.п., DME precision 0.79 ±0.08 / recall 0.79 ±0.09 на дефолтном пороге) честно переобучает именно этот рецепт (аугментация поворотом + PCA(75), отбор модели на аугментированных данных) на каждом из 5 сидов. Это реальная, но не клинически валидированная модель — она демонстрирует механизм, а не готова к диагностическому использованию.

**ML round 4** (попытка поднять DME recall): `MLPClassifier` (лучшая модель по CV) не поддерживает `class_weight`, поэтому испытан oversampling миноритарного класса аугментированными копиями (`app/ml/train.py`, флаг `--minority-oversample`, по умолчанию выключен). Результат отрицательный: при факторах 2x и 4x модель на held-out тесте пропускала **ровно те же 11 снимков** DME (recall остался 0.67), а precision просел до 0.88/0.81 — то есть дисбаланс классов не был узким местом, узкое место — потолок самих признаков (HOG + доменные) на этих конкретных снимках. Флаг оставлен в коде для дальнейших экспериментов, но по умолчанию выключен, чтобы не проиграть уже имеющемуся балансу precision/recall.

**ML round 5** (анализ порога классификации, ⚠️ метод исправлен в round 6 — см. ниже): в отличие от oversampling, порог реально двигает баланс. `train.py` считал precision-recall кривую по вероятности DME **на held-out тесте** и писал в `metrics.json` две альтернативные рабочие точки:
  - лучший F1 при cutoff≈0.53 (почти тот же, что дефолтный 0.5): precision 0.96 / recall 0.67 — то же количество пропущенных случаев;
  - **recall≥0.85** при cutoff≈0.018: precision 0.62 / recall 0.91 — модель пропускает только 3 из 33 DME-снимков вместо 11, ценой роста ложных срабатываний на здоровых снимках (18 из 190 вместо 2).

  По продуктовому решению (проверено с пользователем) этот порог применён в `app/services/report_generator.py` (`DME_SCREENING_THRESHOLD`): для скринингового ассистента, где каждую находку в любом случае проверяет врач, пропущенный отёк хуже лишней проверки. ДМО помечается как находка, требующая очной консультации, начиная с этой вероятности — а не только когда она выше 50% и формально «наиболее вероятна» — с явной пометкой о пониженной уверенности модели в пограничных случаях; сырые проценты по обоим классам в интерфейсе не меняются.

**ML round 6** (исправление утечки данных при подборе порога): подбор порога в round 5 был методологической ошибкой — precision-recall кривая считалась прямо на test-выборке, той же самой, на которой потом репортились финальные цифры. Это классическая утечка: порог, который лучше всего выглядит на конкретных 223 тестовых снимках, не обязательно обобщается на новые данные. Исправлено в `train.py` (`_cv_threshold_analysis`): пороги теперь подбираются через out-of-fold предсказания 4-fold CV **только на train-выборке** (890 снимков), а test-выборка используется один раз — просто чтобы честно оценить (не подобрать) уже выбранные пороги. Честные цифры оказались скромнее:
  - лучший F1 при cutoff≈0.135: precision 0.82 / recall 0.70 (было заявлено 0.96/0.67 — cutoff сместился, но recall почти не вырос);
  - **recall≥0.85 на train CV** при cutoff≈0.042: на честном held-out тесте recall 0.79 / precision 0.68 — заметно скромнее, чем заявленные ранее 0.91/0.62 (0.85 на CV не гарантирует 0.85 на новых данных).

  `DME_SCREENING_THRESHOLD` обновлён с 0.018 на 0.042 (честный recall≥0.85-на-CV порог) — сама продуктовая логика не менялась и уже была согласована в round 5, поменялось только конкретное число после исправления методологии.

**ML round 7** (тесты на логику подбора порога): функции `_select_thresholds`, `_metrics_at_threshold`, `_oversample_minority` были покрыты только сквозным прогоном `train.py` на реальном датасете — ни одного юнит-теста, при том что именно в этой логике уже проехала утечка данных (round 6). Добавлены юнит-тесты (`tests/test_threshold_selection.py`) на синтетических данных без зависимости от датасета. Попутно выяснилось: минимальный порог из `precision_recall_curve` почти всегда даёт recall=1.0 (при нём всё классифицируется как «позитив»), поэтому ветка `high_recall_threshold=None` практически недостижима для разумных `min_recall` — это не баг, но задокументировано тестом, чтобы никто не «исправил» эту ветку во что-то нерабочее.

**ML round 8** (калибровка вероятностей): проверено, не улучшит ли `CalibratedClassifierCV` (sigmoid/isotonic) качество вероятностей модели поверх работы над порогом (round 5-6). На честном held-out тесте:
  - без калибровки: Brier 0.053 / log loss 0.198;
  - **isotonic**: Brier 0.046 / log loss 0.144 — лучше по обеим метрикам в среднем по всей выборке;
  - **sigmoid**: Brier 0.053 / log loss 0.202 — практически без изменений.

  Но на конкретной рабочей точке (recall≥0.85-на-CV, уже применённой в проде) isotonic её портит: precision 0.58 / recall 0.76 против 0.68/0.79 без калибровки — то есть более точная калибровка «в среднем по вероятности» не гарантирует лучшую работу в конкретной точке отсечения, которую реально использует приложение. Sigmoid — нейтрален (не лучше и не хуже в пределах шума на 33 тестовых DME-снимках). Калибровка не применена в проде; `metrics.json` теперь дополнительно хранит `dme_calibration_metrics` (Brier/log loss без калибровки) для отслеживания при будущих переобучениях.

  ⚠️ Черновой скрипт для этого раунда изначально содержал баг в порядке столбцов при вызове `log_loss` (передавал 2D-массив вероятностей в порядке `classes_` вместо порядка меток `y_true`), из-за чего isotonic сперва выглядела катастрофически (log loss ~19 вместо честных 0.14). Исправлено до того, как ушло в `train.py` и в этот README — на будущее: `log_loss` для бинарного случая безопаснее вызывать с 1D-массивом вероятностей положительного класса, а не с 2D-массивом, порядок столбцов которого нужно сверять вручную.

**ML round 9** (текстурные признаки LBP): проверено, добавляют ли Local Binary Patterns (`skimage.feature.local_binary_pattern`) сигнал поверх HOG + доменных признаков — LBP часто хорошо ловит текстуру именно там, где HOG слабее (мелкая, немасштабная зернистость). Два варианта, оба на реальном датасете, тот же train/test-сплит, что и раньше:
  - простой LBP (P=8, R=1, 10-бинная гистограмма) отдельно: cv balanced accuracy 0.673 — намного хуже HOG+domain (0.807), ожидаемо для 10-мерного признака против 1578-мерного;
  - HOG+domain **+** простой LBP: cv 0.802 (не лучше 0.807), test precision 0.88 / recall 0.70 (было 0.92/0.67) — recall чуть вырос, precision чуть просел;
  - HOG+domain **+** multi-radius LBP (P/R = 8/1, 16/2, 24/3, 54 бина): cv 0.807 (то же самое, но с меньшим разбросом по фолдам: ±0.018 против ±0.039) и test precision 0.95 / recall 0.64 (наоборот, precision чуть вырос, recall чуть просел).

  Ни один вариант не даёт чистого улучшения — сдвиги precision/recall в разные стороны у двух конфигураций и в пределах шума на 33 тестовых DME-снимках (один снимок = ~3 п.п.). LBP не добавлен в `features.py`/прод; выводы задокументированы, чтобы не повторять этот же эксперимент.

**ML round 10** (утечка данных по пациентам — крупнее, чем round 6): имена файлов в датасете (`1222_OD_o_2`, `1222_OI_o_1`, ...) — это `<ID пациента>_<глаз>_o_<визит>`. Проверка показала: 1113 снимков принадлежат всего 831 уникальному пациенту — у 25% снимков есть «родственник» от того же пациента (оба глаза и/или повторные визиты). Использовавшийся до этого раунда сплит (`train_test_split` со стратификацией по классу, но **не по пациенту**) пускал снимки одного пациента одновременно и в train, и в test: **79 из 831 пациентов** пересекались между выборками. Модель могла частично опираться на специфичные для пациента признаки (уникальный рисунок сосудов, особенности конкретного визита/камеры), а не только на признаки самого ДМО — это завышало все метрики, включая заглавные "текущие метрики" выше.

  Исправлено: `_group_aware_split` (`train.py`) — `StratifiedGroupKFold` вместо `train_test_split`, группировка по ID пациента, гарантирующая, что ни один пациент не попадёт одновременно в обе выборки. То же самое исправление внесено во внутренние CV на train-выборке (`select_best_model`, `_cv_threshold_analysis`) — иначе группировка на верхнем уровне не спасла бы от такой же утечки внутри. Честные цифры на patient-grouped сплите:
  - held-out test accuracy 92.8% (было 94.2%), DME precision 0.84 / recall 0.64 (было 0.92 / 0.67);
  - **recall≥0.85-на-CV** порог сместился на 0.037 (было 0.042): честный test recall 0.88 / precision 0.57 (round 6 давал recall 0.79 / precision 0.68 на сплите с утечкой).

  `DME_SCREENING_THRESHOLD` обновлён на 0.037. Это снова техническая поправка методологии (сплит теперь корректен), а не новое продуктовое решение — сам выбор «флагировать ДМО ради recall» остаётся тем же, что согласован в round 5. Добавлен юнит-тест (`tests/test_group_split.py`), проверяющий, что ни один пациент не оказывается одновременно в train и test.

**ML round 11** (снижение размерности перед SVM): 1578-мерный HOG+domain вектор против ~700-900 обучающих снимков (после патч-группировки round 10) — классический high-dim/low-N режим, рискованный особенно для SVM. Проверен `PCA` разной размерности перед каждым кандидатом на честном patient-grouped CV:
  - `PCA(20-75)+MLP`: cv balanced accuracy 0.81-0.83 — в пределах шума относительно baseline MLP (0.817), не улучшение;
  - `PCA(30)+SVM`: cv balanced accuracy **0.879** (±0.013) — заметно выше любого варианта без понижения размерности (0.816-0.831), разница больше суммарного разброса по фолдам.

  `svm_rbf_pca30` добавлен как новый кандидат в `_candidate_estimators()` и честно выиграл отбор через существующий механизм `select_best_model` (не выбран вручную). На held-out тесте: accuracy 92.8% (то же самое), но DME precision 0.71 / recall 0.88 (F1 0.78) — заметно другой баланс, чем у прежней MLP (0.84/0.64, F1 0.72): новая модель уже на дефолтном 50%-cutoff даёт recall, сравнимый с тем, что раньше давал специальный скрининговый порог. Пересчитан и `DME_SCREENING_THRESHOLD` под новую модель — honest recall≥0.85-на-CV порог для неё 0.260 (test recall 0.88 / precision 0.66, примерно та же точка, что и дефолтный cutoff — подтверждена тем же методом CV-подбора для консистентности с round 6/10).

  Смена алгоритма (не только гиперпараметров) — это техническое решение через уже существующий, объективный механизм отбора модели по CV, а не новое клиническое решение; сам подход «показывать оба процента, флагировать по порогу» не менялся.

**ML round 12** (проверка устойчивости round 11): на датасете такого размера (33-51 DME в тесте, ~130-190 DME в train в зависимости от сплита) единичный CV-результат может оказаться просто удачным сидом — round 6 и round 10 уже показали, как легко здесь ошибиться. Перепроверено на нескольких случайных сидах, без изменений кода:
  - варьировался сид **фолдов CV** (тот же train/test, что в round 11): `PCA(30)+SVM` стабильно 0.857-0.883 против MLP 0.799-0.819 — отрыв сохраняется на всех сидах;
  - варьировался сид **самого train/test сплита**: `PCA(30)+SVM` снова стабильно впереди (cv 0.866-0.879 против MLP 0.761-0.817), test recall держится в диапазоне 0.86-0.94 (precision 0.71-0.80) на трёх разных сплитах.

  Round 11 подтверждён — это не артефакт конкретного сида `random_state=42`. Изменений в коде нет, это верификационный раунд.

**ML round 13** (тонкая настройка PCA(30)+SVM — не осталось ли лёгкого выигрыша): проверено, не близко ли выбранное в round 11 число компонент/гиперпараметры SVM к границе, где можно было бы легко улучшить результат.
  - число компонент PCA в районе 30: 15→0.867, 20→**0.881**, 25→0.875, 30→0.879, 35→0.878 — плато в пределах шума (±0.013-0.018), 30 не хуже соседних значений;
  - grid по `C`/`gamma` вокруг дефолтных `SVC(C=1.0, gamma="scale")`: ни одна из проверенных комбинаций (C∈{0.1,1,10}, gamma∈{scale,0.01,0.001}) не обошла дефолт (0.879); `gamma=0.01` вообще катастрофична (cv=0.5, случайное угадывание) — судя по всему, неподходящий масштаб для этих признаков после PCA.

  Уже выбранная конфигурация (round 11) оказалась близка к оптимуму в проверенной области — легко доступного выигрыша тонкой настройкой не нашлось. Изменений в коде нет.

**ML round 14** (утечка через дубликаты файлов — group-aware сплит round 10 не полная защита): по MD5-хешу содержимого файла найдено **12 пар байт-в-байт идентичных снимков**, оформленных в датасете под **разными** ID пациентов (соседние/близкие номера, например `1330` и `1348`) — похоже на артефакт дублирования записи в исходном датасете, не ошибку разметки: метки DME внутри каждой пары совпадают. Поскольку `_group_aware_split` группирует только по ID пациента, эти дубликаты его не защищают: на текущем сплите (`random_state=42`) **2 из 12 пар всё равно оказались по разные стороны** train/test — модель могла в буквальном смысле увидеть тот же снимок на обучении и тривиально узнать его на тесте.

  Исправлено: `_merge_duplicate_groups` (`train.py`) — union-find, объединяющий ID пациентов, если у них хоть один байт-идентичный снимок, до вызова `_group_aware_split`. Уникальных групп стало 820 (было 831). Добавлен юнит-тест (`tests/test_duplicate_groups.py`).

  Побочный эффект: объединение части групп в более крупные блоки грубее квантует стратификацию по классу — на конкретном `random_state=42` тестовая выборка сократилась с 33 до 25 DME-снимков, а precision на этом конкретном сплите просела до 0.47 (recall остался 0.84). Проверка на других сидах сплита (7, 99, 123) показала precision 0.61-0.72 при recall 0.82-0.90 — то есть 0.47 не признак того, что модель стала хуже, а особенность именно этого воспроизводимого разбиения. `DME_SCREENING_THRESHOLD` обновлён под честный recall≥0.85-на-CV порог для этого сплита — 0.350 (test recall 0.84 / precision 0.50).

**ML round 15** (усреднение по сидам сплита — вместо доверия одному числу): round 14 показал, что precision на этом маленьком, сгруппированном по пациентам датасете может скакать от 0.47 до 0.72 в зависимости от сида сплита — единичное число легко может ввести в заблуждение. `train.py` теперь честно переобучает **тот же тип модели**, что победил в отборе, на 5 разных сплитах (сиды 42, 7, 99, 123, 2024) и пишет среднее±стд в `metrics.json` (`multi_seed_evaluation`), используя только held-out тестовые метрики (без изменения того, на чём в тот момент обучался финальный чекпоинт — см. round 16 про то, что изменилось дальше).

  Результат: test accuracy 0.905±0.016, DME precision 0.643±0.096, DME recall 0.865±0.038 — сплит `random_state=42` (precision 0.47) оказался на пессимистичном краю именно по precision, но recall и accuracy у него вполне типичные. Заглавные метрики выше теперь приводят оба числа — усреднённое (типичное) и то, что было на конкретном сплите — вместо того, чтобы выдавать один сплит за окончательную правду.

**ML round 16** (финальный чекпоинт — на 100% данных, а не только на 80%): все метрики выше честно измерены на модели, обученной только на train-сплите (~80% данных) — это правильный способ оценить обобщение. Но датасет маленький (1113 снимков, из них только 167 DME), и каждый размеченный снимок ценен. Стандартная практика ML: после того как валидация подтвердила качество подхода, финальный чекпоинт **дообучается на всех 100% данных** перед отправкой в прод — это не может ухудшить результат (может только помочь, при условии отсутствия сдвига распределения между train и test, что здесь так и есть, поскольку тестовые снимки взяты из того же датасета).

  Реализовано в `train.py`: после подсчёта held-out метрик, анализа порога, калибровки и multi-seed оценки — те по-прежнему честно измерены на модели, обученной только на train-сплите — финальный чекпоинт (`model = OCTClassifier(...); model.fit(X_all, y_all)`) переобучается на всех 1113 снимках того же типа модели (`svm_rbf_pca30`), что выиграл отбор, и именно этот чекпоинт сохраняется и используется в проде. `metrics.json` получил поле `shipped_checkpoint_trained_on_full_dataset: true`, явно поясняющее, что цифры в model card — честная оценка *подхода*, а не прямое измерение производительности именно этого финального артефакта (который не был напрямую протестирован на held-out данных, поскольку все они уже пошли в его обучение).

**ML round 17** (ансамбль и RandomForest+PCA — оба хуже одиночного SVM): проверено, не улучшит ли `svm_rbf_pca30` (round 11) комбинирование с другими моделями на честном patient-grouped CV:
  - `RandomForest` после `PCA(30)`: cv balanced accuracy 0.624 — намного хуже одиночного SVM (0.902), PCA явно не помогает RandomForest так же, как SVM;
  - `VotingClassifier` (soft voting, `svm_rbf_pca30` + `mlp_64`), равные веса: cv 0.855 — хуже одиночного SVM;
  - тот же voting с весами 2:1 в пользу SVM: cv 0.858 — всё ещё хуже.

  И ансамблирование, и RF+PCA тянут результат вниз, а не вверх: `svm_rbf_pca30` настолько сильнее слабых моделей, что усреднение вероятностей с ними просто портит его собственный, уже хороший результат. Изменений в коде нет.

**ML round 18** (доменные признаки всё ещё нужны? — перепроверка на новом пайплайне): в round 3 доменные признаки (толщина сетчаточной полосы, доля гипорефлективных зон — всего 10 чисел) добавили к HOG и получили «небольшой, но измеримый прирост» — но это было ещё на старой MLP-модели, до патч-группировки (round 10) и смены модели на PCA+SVM (round 11). Перепроверено на честном patient-grouped CV с текущим пайплайном:
  - `HOG + domain` (текущий, `svm_rbf_pca30`): cv 0.902;
  - только `HOG` (те же PCA(30)+SVM): cv 0.894 — разница в пределах шума фолдов (±0.024-0.027);
  - только доменные признаки (10 чисел, без PCA — размерность и так низкая): cv **0.859** — удивительно сильный результат для всего 10 простых чисел, почти на уровне полного HOG-вектора (1568-мерного).

  Комбинация по-прежнему оправдана (0.902 — лучшее число из трёх), хоть прирост от добавления HOG к домену (или домена к HOG) и небольшой относительно шума. Главный интересный вывод — доменные признаки несут реальный, существенный сигнал сами по себе, а не просто шум: это хорошая независимая проверка, что эвристика сегментации (`segmentation.py`) действительно улавливает что-то осмысленное про толщину сетчатки и тёмные зоны, а не выдаёт случайные числа. Изменений в коде нет.

**ML round 19** (⚠️ устойчивость к реальным фото — найдена серьёзная уязвимость к повороту): толчком послужил реальный снимок пользователя — фотография экрана/распечатки ОКТ с телефона, а не прямой цифровой экспорт, как в датасете обучения. Проверена устойчивость шипованной модели (`svm_rbf_pca30`) к типичным искажениям такой съёмки — на held-out тестовой выборке, к каждому снимку применено одно из искажений:
  - **JPEG-сжатие** (quality=30 и даже quality=10 — сильное сжатие): accuracy 0.947-0.956, DME precision/recall не хуже базовых (0.68/0.92) — модель устойчива;
  - **яркость** (×0.7 темнее / ×1.4 ярче, имитация недосвета/пересвета) и **контраст** (×0.6, «смытое» фото): accuracy 0.947-0.951 — тоже устойчива;
  - **поворот на 5°**: accuracy падает до 0.893-0.911, DME precision — с 0.68 до 0.51-0.56;
  - **поворот на 15°**: accuracy 0.591, DME precision 0.05 / recall 0.16 — модель полностью ломается, предсказания на уровне случайного шума.

  Причина ожидаема и объяснима: доменные признаки (`segmentation.py`) строятся на построчном анализе яркости вдоль оси глубины скана — поворот снимка полностью искажает этот профиль; HOG тоже завязан на фиксированную сетку ячеек, чувствительную к ориентации. Для self-service платформы, где пользователи сами фотографируют распечатки/экраны (ровно как в присланном примере), даже небольшой перекос камеры — совершенно реалистичный сценарий, и сейчас он способен незаметно сломать анализ без явного предупреждения пользователю. Это не пофикшено в этом раунде (требует либо детектора перекоса в `quality_check.py`, либо признаков, устойчивых к повороту, — оба варианта нетривиальны и заслуживают отдельного раунда/продуктового решения), но задокументировано как реальный, воспроизводимый пробел, а не гипотетический.

**ML round 20** (попытка авто-deskew — неоднозначный результат, не внедрён): проверен самый очевидный фикс round 19 — перебор угла поворота (от -20° до +20°, шаг 2°) с выбором угла, максимизирующего «пиковость» (стд.) построчного профиля яркости, перед извлечением признаков:
  - **поворот 15° + deskew**: accuracy восстанавливается с 0.591 до **0.898** (средний найденный угол коррекции 14.0°, близко к истинным 15°) — эвристика реально работает на сильных поворотах;
  - **поворот 5° + deskew**: 0.898 vs 0.893 без коррекции — почти не меняется (при малом повороте пиковость не даёт chёткого сигнала);
  - **⚠️ baseline БЕЗ поворота + deskew** (проверка на «не навреди»): accuracy **падает** с 0.942 до 0.880 — эвристика иногда находит ложный «оптимальный» угол (в среднем 4.3°) даже на уже правильно ориентированных снимках, портя то, что не было сломано.

  Deskew — реальный, но обоюдоострый инструмент: спасает сильно повёрнутые снимки, но вредит нормальным. Раз в реальном датасете обучения снимки уже выровнены (round 19 не находил проблем на них), включать коррекцию для всех подряд — чистый проигрыш на типичном случае. Не внедрено в прод: нужен более умный триггер (например, применять коррекцию только когда есть независимый сигнал, что снимок действительно повёрнут, а не всегда) — это отдельная, нетривиальная задача, оставлена как открытый пункт вместе с round 19.

**ML round 21** (попытка триггера для deskew — тоже не сработала): проверено самое очевидное решение открытого вопроса round 20 — применять коррекцию только если найденный угол даёт заметный выигрыш «пиковости» относительно угла 0° (порог `margin`), а не всегда брать лучший угол. Перебраны 4 значения порога (1.05 / 1.08 / 1.15 / 1.25 — требуемое относительное превышение пиковости):

  | margin | baseline (без поворота) | доля «исправленных» | поворот 5° | поворот 15° |
  |---|---|---|---|---|
  | без триггера (round 20) | 0.880 | 100% | 0.898 | 0.898 |
  | 1.05 | 0.880 | 48% | 0.907 | 0.898 |
  | 1.08 | 0.880 | 42% | 0.902 | 0.898 |
  | 1.15 | 0.889 | 30% | 0.893 | 0.889 |
  | 1.25 | 0.898 | 18% | **0.889** (хуже, чем без коррекции: 0.893) | 0.867 |
  | без поворота, без deskew (истинный baseline) | **0.942** | — | — | — |

  Чистого порога не нашлось: с ростом margin доля ложных «исправлений» на нормальных снимках падает (48%→18%), но baseline accuracy так и не приближается к истинным 0.942 (максимум 0.898), а чувствительность к реальным поворотам падает пропорционально — при margin=1.25 коррекция для умеренного поворота (5°) уже хуже, чем вообще её не делать (0.889 vs 0.893). Причина: «пиковость» построчного профиля яркости и так сильно варьируется между снимками из-за анатомии и качества съёмки — эта естественная вариация того же порядка, что и сигнал от самого поворота, поэтому простой относительный порог не может надёжно отличить одно от другого. Нужен принципиально другой, независимый сигнал перекоса (например, поиск доминирующих линий/краёв через преобразование Хафа), а не повторное использование той же метрики, что и для решения о коррекции. Изменений в коде нет — открытый вопрос round 19/20 остаётся открытым.

**ML round 22** (независимый сигнал перекоса — тоже слишком шумный, и стало ясно почему): реализован сигнал, который round 21 предложил как альтернативу «пиковости» — доминирующая ориентация градиента (через приём с удвоением угла, устойчивый к 180°-неоднозначности направления края), которая для правильно ориентированного скана должна быть вертикальной; отклонение от вертикали = оценка угла поворота. Проверено на 60 тестовых снимках с разными истинными углами поворота (0°/5°/15°), с вариантами по порогу силы градиента (95-й/98-й перцентиль) и по области анализа (весь снимок vs только зона сетчатки):

  - оценка **несмещённая в среднем**: медиана при истинном 0° близка к 0, при 5° — около -5, при 15° — около -15 (знак — просто соглашение направления);
  - но **очень шумная на уровне отдельного снимка**: std 12-17° почти во всех вариантах — сопоставимо с самим сигналом от поворота на 5-15°;
  - лучший найденный вариант (98-й перцентиль, только зона сетчатки) снизил std для угла 5° до **6.0°** — заметное улучшение, но std на истинном 0° почти не изменился (11.8°), то есть по-прежнему множество лже-срабатываний на нормальных снимках.

  Более глубокий вывод, чем просто «метрика неудачная»: скорее всего дело в том, что у разных пациентов заметно отличается **естественная кривизна сетчатки** (у кого-то более плоская, у кого-то более выпуклая) — это варьирует «глобальную ориентацию» снимка ничуть не меньше, чем реальный поворот камеры на 5-15°. Простая глобальная оценка ориентации (любым методом — через яркость или через градиент) не может отличить «камеру наклонили» от «у этого пациента такая форма сетчатки». Надёжное решение потребовало бы моделировать саму форму кривой границы сетчатки и искать асимметрию относительно неё, а не глобальный угол — это существенно больший объём работы, выходящий за рамки одного раунда. Изменений в коде нет; открытый вопрос round 19-21 остаётся открытым, но диагноз стал точнее.

**ML round 23** (⚠️ устойчивость к повороту через аугментацию обучения — реальный выигрыш, но с честной оговоркой о recall): rounds 20-22 пытались обнаружить/исправить поворот во время инференса и не нашли надёжного сигнала (см. выше). Round 23 пробует другой подход — заложить устойчивость прямо в обучение: к каждому обучающему снимку добавляются копии, повёрнутые на -10°/-5°/+5°/+10° (`_rotation_augment` в `train.py`), с сохранением группы пациента у каждой копии (та же защита от утечки, что и в `_oversample_minority` выше — иначе повёрнутые копии одного снимка могли бы разъехаться по разным фолдам group-aware CV). На честном held-out тесте (тот же сплит, что и в round 19):

  | | без поворота | +5° | +15° | +20° (за пределами диапазона аугментации) |
  |---|---|---|---|---|
  | базовая модель (без аугментации) | acc 0.876, DME p=0.47/r=0.84 | acc 0.831, p=0.37/r=0.76 | acc 0.453, p=0.12/r=0.64 | — |
  | + аугментация поворотом | acc 0.911, p=0.58/r=0.76 | acc 0.911, p=0.57/r=0.80 | acc 0.809, p=0.34/r=0.80 | acc 0.600, p=0.14/r=0.52 |

  Это настоящий, чистый выигрыш по общей точности и устойчивости: accuracy на неповёрнутых снимках выросло (0.876→0.911), и она **не проседает вплоть до 15°** (0.831/0.453 → 0.911/0.809) — round 19 больше не актуален для этого диапазона поворота. Полный прогон через `train.py` на реальном датасете подтвердил те же цифры (test accuracy 0.911, DME precision 0.58/recall 0.76) и не сломал ни один из существующих механизмов (group-aware CV, отбор модели, множественные сиды).

  ⚠️ Но была честная оговорка: recall DME на **клиническом скрининговом пороге** (`DME_SCREENING_THRESHOLD`, специально смещённом в сторону recall — см. `report_generator.py`) на этом конкретном сплите (`random_state=42`, том самом, что зафиксирован в проде) **упал**, а не вырос — с 0.84 до 0.72 на CV-подобранном высокорекольном пороге аугментированной модели (0.286). Round 23 изначально был внедрён в код (флаг `--no-rotation-augment` для отката), но **не отправлен как новый прод-чекпоинт** без проверки на нескольких сидах — именно потому, что recall — не абстрактная метрика, а мера того, сколько реальных случаев отёка модель не пропустит.

  **Проверка на 5 сидах сплита (42, 7, 99, 123, 2024)** сняла эту неопределённость:

  | сид | accuracy: база → aug | DME precision (порог): база → aug | DME recall (порог): база → aug |
  |---|---|---|---|
  | 42 | 0.876 → 0.911 | 0.50 → 0.62 | **0.84 → 0.72** |
  | 7 | 0.907 → 0.930 | 0.65 → 0.84 | 0.84 → 0.84 |
  | 99 | 0.907 → 0.920 | 0.70 → 0.74 | 0.80 → 0.80 |
  | 123 | 0.913 → 0.935 | 0.58 → 0.66 | 0.93 → 0.90 |
  | 2024 | 0.923 → 0.941 | 0.71 → 0.77 | 0.92 → 0.87 |

  Сид 42 (тот, что зафиксирован в проде) оказался **худшим** случаем для recall из пяти проверенных, а не типичным — на 4 из 5 сидов просадка гораздо меньше (0-5 п.п.) или отсутствует вовсе. В среднем по 5 сидам: accuracy 0.905→0.927 (растёт на всех 5 из 5), DME precision на пороге растёт на всех 5 из 5, DME recall на пороге в среднем просаживается скромно (0.866→0.826, ~4 п.п.), а не драматично, как показал единственный сплит `random_state=42`.

  **Решение: round 23 отправлен в прод.** Устойчивость к повороту снимка — это не абстрактное улучшение, а прямое попадание в реальный сценарий использования платформы (пользователи фотографируют распечатки/экраны телефоном, ровно как показал реальный пример round 19), а средняя просадка recall (~4 п.п.) — не то же самое, что казавшийся драматичным разовый результат на одном сплите. Чекпоинт (`oct_classifier.joblib`) и модель-карта (`metrics.json`) переобучены и заменены командой `python -m app.ml.train --data-dir ...` с аугментацией поворотом, включённой по умолчанию.

  Небольшой технический хвост сразу после отгрузки: `_multi_seed_evaluation` (round 15) при этом продолжал переобучать **старый**, не аугментированный рецепт на каждом из 5 сидов — поле `multi_seed_evaluation` в `metrics.json` описывало не ту модель, что реально ушла в прод. Исправлено тем же раундом: функция теперь принимает исходные изображения (а не готовые признаки) и опционально прогоняет `_rotation_augment` перед обучением на каждом сиде — дороже (5-кратное извлечение признаков вместо переиспользования готовой матрицы), но `_multi_seed_evaluation` и так уже документирован как разовая проверочная процедура, не горячий путь. Пересчитанные честные цифры аугментированного рецепта по 5 сидам: test accuracy 92.7% (±1.1 п.п.), DME precision 0.73 (±0.09) / recall 0.82 (±0.05) на дефолтном пороге — совпадает с ручной многосидовой проверкой, что и обосновала решение выше.

**ML round 24** (унификация доменных признаков с новой сегментацией — отрицательный по точности результат, положительный по качеству кода): после переписывания `segmentation.py` под per-column tracking (см. секцию "Сегментация" выше) классификаторные доменные признаки (`app/ml/features.py`) остались на **старой** версии той же идеи — однa усреднённая по всей ширине снимка линия для оценки границ сетчатки, вручную продублированная и хранившаяся в синхроне только комментарием (ровно тот же паттерн дублирования, что уже нашёлся и был исправлен для `LAYER_LABELS_RU` и `DME_SCREENING_THRESHOLD`). Общие примитивы (`smooth`, `tissue_extent`, `flatten_band`) вынесены в `app/ml/signal_utils.py`, которым теперь пользуются и `segmentation.py`, и `features.py` — заодно удалён `_gradient_magnitude` в `segmentation.py`, ставший мёртвым кодом после round про новую карту слоёв.

  Гипотеза была: раз новый `tissue_extent` устойчивее к кривизне сетчатки (per-column, а не один глобальный профиль), доменные признаки классификатора должны стать точнее и/или устойчивее к повороту снимка. Проверено на реальном датасете, честно:
  - **Точность (без поворота, group-aware CV)**: старые признаки 0.896 (±0.016), новые 0.891 (±0.016) — разница внутри одного стандартного отклонения, статистически неразличимо.
  - **Устойчивость к повороту** (тот же тест, что и round 19/23): при +5° и +15° старые и новые доменные признаки дают **практически идентичный** результат (0.831/0.453 против 0.831/0.458) — гипотеза не подтвердилась. Вероятная причина: HOG-признаки (1578 из ~1588 измерений вектора) настолько доминируют в решении классификатора, что 10 доменных признаков почти не влияют на итог ни в какую сторону.

  Решение: несмотря на нулевой эффект на точность, унификация всё равно того стоит — устраняет реальный риск рассинхронизации (тот самый паттерн, что уже дважды кусал этот проект) и убирает мёртвый код. Чекпоинт переобучен для согласованности train/inference (сами признаки численно чуть меняются, хоть итоговая точность и не меняется) — test accuracy 91.6% (в пределах шума от 91.1% до round 24). Полный набор тестов (38) проходит.

**ML round 26** (аугментация зеркальным отражением — скромный, смешанный результат, не отгружен): снимки ОКТ размечены по глазу (OD/OS в имени файла), а зеркальное отражение по горизонтали не трогает ось глубины (вертикаль), на которой строится весь анализ слоёв — низкий риск, стандартный приём для такого рода данных, ещё не пробовался. Проверено: к уже аугментированному поворотом обучающему набору (round 23) добавлены ещё и зеркально отражённые копии (обучающая выборка выросла вдвое, 4390→8780 снимков). На честном held-out тесте:

При этом полная интеграция означала бы удвоение и без того уже долгого обучения (round 23 занимает ~38 минут; полная аугментация поворотом+отражением почти наверняка займёт больше часа) ради скромного, ещё не проверенного на нескольких сидах эффекта. Не отгружено в прод: результат зафиксирован честно, но решение о том, стоит ли скромный выигрыш кратного увеличения времени обучения, требует отдельной многосидовой проверки (как это было сделано для round 23 перед отгрузкой) — открытый пункт для следующего раунда.

  Но нашлось нечто более важное, чем сам параметр PCA: `select_best_model` (отбор типа модели среди кандидатов) по архитектуре работал на **неаугментированных** данных — так было спроектировано намеренно в round 23 ("отбор модели выше по-прежнему работает на неаугментированном сплите, соответствуя методологии всех предыдущих раундов"). Проверка **на тех же неаугментированных ~878 снимках**, что реально видел `select_best_model`, дала **противоположный** результат: `svm_rbf_pca30` — 0.8705 (±0.0201) против `svm_rbf_pca75` — 0.8564 (±0.0414), т.е. PCA(30) там выигрывал. Просто заменить число компонент в коде (или добавить `svm_rbf_pca75` как ещё одного кандидата) означало бы, что механизм отбора модели, не меняя своей логики, никогда не выберет более удачный для аугментированных данных вариант — потому что сам отбор шёл на других данных, чем итоговое обучение.

  Это был не баг конкретной строки кода, а разрыв на уровне архитектуры: отбор типа модели (round 11's методология) и финальное обучение (round 23's аугментация) работали в двух разных режимах данных, и оптимальный гиперпараметр отличался между ними. Перед тем как чинить, проверено (round 28), не сломает ли перенос отбора на аугментированные данные сам выбор ТИПА модели (не только числа компонент PCA) — на всех 5 сидах свм+PCA по-прежнему уверенно обходит MLP/RandomForest/обычный SVM (разница в 0.15-0.25 по balanced accuracy), т.е. сама иерархия типов моделей устойчива, меняется только то, какой вариант PCA внутри неё выигрывает.

  **Исправлено**: аугментация поворотом в `train.py` теперь применяется *до* `select_best_model`, а не после — отбор модели и финальное обучение видят одни и те же данные. `svm_rbf_pca75` добавлен как ещё один кандидат (не заменяя `svm_rbf_pca30`, чтобы отбор по-прежнему выбирал сам, а не по хардкоду). На реальном датасете `select_best_model` теперь честно выбирает `svm_rbf_pca75` (cv balanced accuracy 0.867 против 0.857 у pca30). Итог на честном held-out тесте — выигрыш по всем метрикам сразу, а не компромисс: accuracy 0.916→0.936, DME precision 0.59→0.77, recall на чувствительном скрининговом пороге **0.72→0.93** (сам порог — 0.123, подобран автоматически через CV, ничего не редактировалось вручную). Это полностью снимает компромисс recall из round 23 — новая модель одновременно точнее и чувствительнее к отёку, а не одно за счёт другого. Чекпоинт переобучен и отгружен. Полный набор тестов (42) проходит.

**Round 36** (детализация карты слоёв сетчатки по референсу пользователя — с честной находкой и фиксом реальной регрессии по пути): пользователь прислал референс реального HD-OCT снимка с подписанными слоями (ILM, NFL, GCL, IPL, INL, OPL, ONL, ELM, IS/OS, RPE, хориоидея, отметка фовеа) и попросил развить карту сегментации до похожего уровня детализации — до этого раунда карта выделяла только 5 объединённых полос (NFL/GCL, IPL/INL, OPL/ONL, фоторецепторы, RPE).

Пользователь подтвердил через `AskUserQuestion` средний вариант — 8 слоёв (NFL, GCL/IPL, INL, OPL, ONL, IS/OS+фоторецепторы, RPE, хориоидея — без выделения ELM отдельной линией) вместо полных ~10 из референса, плюс отметку фовеа, в текущем визуальном стиле (полупрозрачные цветные полосы + легенда).

Нашёл это не на синтетике, а визуально сравнив рендер на реальном снимке датасета со старой версией. Исправление — не подбор параметров, а архитектурное: верхняя и нижняя границы (ILM и внешний край хориоидеи) теперь берутся из уже проверенного в проекте `signal_utils.tissue_extent` (тот же примитив, что использует детектор патологических зон и доменные признаки классификатора), а поиск промежуточных границ ограничен этой полосой — шум фона физически исключён из поиска, а не просто реже выбирается.

Добавлены тесты (`test_segmentation.py`): регрессионный тест на синтетическом снимке (границы не должны уезжать за пределы полосы ткани) и два теста на детекцию фовеа (находит явный провал по центру, не находит его на плоском снимке без провала — важно не выдумывать находку, если её нет). Проверено визуально на нескольких реальных снимках датасета и end-to-end в браузере (Playwright: регистрация → загрузка снимка → карточка "Толщина слоёв сетчатки" на странице исследования показывает все 8 слоёв, PDF/отчёт не ломаются). `frontend/src/lib/labels.ts` обновлён в паре с бэкендом (тест `test_layer_labels_sync.py` проверяет синхронность). Полный набор тестов (49) и `tsc --noEmit` проходят.

**Round 37** (детализация карты патологий по референсу пользователя — клинические примеры сегментации кист/жидкости/мембран, первый шаг из шести категорий): пользователь прислал 3 референса клинических отчётов ИИ-анализа ОКТ с разбивкой находок по конкретным типам патологии — интраретинальные кисты (голубой), субретинальная жидкость (зелёный), отслойка пигментного эпителия (оранжевый), субретинальный гиперрефлективный материал (жёлто-зелёный), ретинальные друзы (жёлтый), эпиретинальная мембрана (красный) — вместо одной общей категории "гипорефлективная зона", которая была раньше. Пользователь явно сказал: "я понимаю что это со временем... давай идти к этому" — то есть согласился на постепенное движение, а не ждёт всех 6 категорий сразу.

Честно оценил, что реализуемо прямо сейчас без выдумывания сигнала: round 36 уже даёт границу RPE (реальную, отслеживаемую по снимку), которая делит сетчатку на анатомически осмысленные зоны. Использовал её, чтобы честно разделить прежний единый детектор тёмных зон на 2 категории по тому, ГДЕ относительно этой границы находится тёмное пятно — интраретинальные кисты/жидкость (выше комплекса фоторецепторы/RPE, где кисты классически и появляются — INL/OPL/ONL) и субретинальная жидкость (на уровне и ниже этого комплекса, до хориоидеи). Это грубое, но реальное анатомическое разделение, а не произвольная перекраска одного и того же пятна в два цвета.

Остальные 4 категории референса **сознательно не реализованы в этом раунде**: эпиретинальная мембрана, отслойка пигментного эпителия, друзы и субретинальный гиперрефлективный материал требуют анализа формы/контура линии RPE (выпуклости, разрывы), а не простого порога по яркости — это качественно другая, более рискованная задача (легко получить ложное "Выявлено" на том, что звучит как конкретный клинический диагноз). Решил не торопиться с шаткой эвристикой ради галочки, а честно отметить это как открытую работу — и в интерфейсе, и в тексте автозаключения.

Технически: `_detect_pathology_zones` (был один вызов на весь снимок) теперь вызывается дважды — на диапазон boundaries[0:5] (интраретинально) и boundaries[6:8] (субретинально); легенда карты сегментации слоёв и карты патологий переиспользуют общий хелпер раскладки (`_compose_legend_canvas`, вынесен из дублировавшегося кода). `pathology_zone_count: int` в схеме/БД/API заменён на `pathology_findings: list[{key, label_ru, color, detected, zone_count}]` (без бэкомпат-костыля — версия всё ещё 0.1.0, реальных пользователей с сохранённой историей нет). На странице исследования карта патологий теперь показывает чек-лист по категориям (цветная точка + "Выявлены (N)" / "Не выявлены"), похожий на панели C/F из референсов пользователя.

По пути повторно поймал печатный баг того же типа, что чинили в round 18: выросший объём текста (чек-лист патологий + 8 слоёв из round 36) перестал помещаться в 2 страницы PDF — `break-inside: avoid` на длинной текстовой карточке AI-заключения заставлял её (и всё после неё) целиком прыгать на следующую страницу, оставляя почти пустую 3-ю. Исправил не косметикой (уменьшением отступов — это не помогло), а архитектурно: длинной текстовой карточке разрешено разрываться между страницами как обычному тексту (`break-inside: auto`), а не только компактным визуальным карточкам. Проверено генерацией настоящего PDF (PyMuPDF, подсчёт страниц и текста на каждой) до и после — ровно 2 страницы, разрыв текста между ними не режет слова.

Проверено: 52 бэкенд-теста (включая новый `test_detect_pathology_findings_splits_by_category`, который разводит два синтетических тёмных пятна по разным категориям и проверяет, что каждое попадает только в свою), Vitest (11) и `tsc --noEmit` проходят; end-to-end в браузере на реальном снимке (чек-лист корректно показывает найденные зоны по категориям), PDF (2 страницы, не 3), мобильная раскладка (390px, без горизонтального overflow).

Переобучить (или обучить на любом другом датасете с такой же структурой) можно так:

```bash
git clone https://github.com/Traslational-Visual-Health-Laboratory/OCT-AND-EYE-FUNDUS-DATASET.git
cd backend
python -m app.ml.train --data-dir /path/to/OCT-AND-EYE-FUNDUS-DATASET
```

Без `--data-dir` скрипт обучается на процедурно сгенерированной синтетике (`app/ml/synthetic_dataset.py`) — это smoke-test пайплайна, а не рабочая модель; полезно только чтобы быстро проверить, что код обучения/инференса не сломан.

Скрипт сохранит новый чекпоинт в `app/ml/artifacts/oct_classifier.joblib`; перезапустите backend, чтобы он подхватил новые веса (инференс кэширует загруженную модель в памяти процесса).

## Миссия

Сделать высокоточную диагностику заболеваний сетчатки доступной каждой клинике независимо от ее размера, сократить время анализа исследований и повысить качество медицинской помощи за счет современных технологий искусственного интеллекта.

## Проблема

Сегодня большинство исследований ОКТ анализируются врачом вручную. Этот процесс имеет несколько недостатков:

- высокая нагрузка на специалистов;
- человеческий фактор;
- различия в опыте врачей;
- длительное время подготовки заключения;
- ограниченный доступ к опытным офтальмологам в небольших городах.

При увеличении количества исследований растет вероятность пропустить ранние признаки заболевания.

## Решение

OCTera автоматически анализирует медицинские изображения и помогает врачу принимать решения.

После загрузки ОКТ-снимка система:

1. Проверяет качество изображения.
2. Выполняет предварительную обработку данных.
3. Анализирует анатомические структуры сетчатки.
4. Выполняет сегментацию всех основных слоев.
5. Находит патологические изменения.
6. Определяет наиболее вероятные заболевания.
7. Рассчитывает вероятность каждого диагноза.
8. Строит карту обнаруженных патологий.
9. Генерирует подробное медицинское заключение.
10. Сохраняет результаты исследования.

Полный анализ занимает несколько секунд.

## Основные возможности

### Автоматический анализ ОКТ

Система определяет:

- возрастные изменения;
- макулярный отек;
- диабетический макулярный отек;
- возрастную макулярную дегенерацию;
- глаукому;
- эпиретинальную мембрану;
- серозную отслойку;
- нарушения структуры сетчатки;
- атрофические изменения;
- другие патологии.

### Сегментация

Нейросеть автоматически выделяет:

- внутренние и наружные слои сетчатки;
- область макулы;
- жидкость;
- кисты;
- зоны повреждений;
- патологические образования.

Полученная карта помогает врачу быстрее интерпретировать результаты исследования.

### AI-заключение

После анализа система автоматически формирует:

- описание исследования;
- найденные изменения;
- предполагаемый диагноз;
- уровень уверенности модели;
- рекомендации по дальнейшему обследованию.

Заключение может использоваться как предварительная версия для врача.

### Визуализация

Пользователь получает:

- исходное изображение;
- тепловую карту внимания модели;
- карту сегментации;
- выделенные патологические области;
- показатели толщины слоев;
- вероятности заболеваний.

### API

Платформа предоставляет REST API для интеграции с:

- медицинскими информационными системами;
- PACS;
- лабораторными системами;
- облачными сервисами;
- мобильными приложениями.

### История исследований

Для каждого исследования сохраняются изображения, результаты анализа и диагнозы — это уже реализовано (список своих исследований в личном кабинете). Сравнение динамики между исследованиями одного пользователя во времени — в планах (см. «Текущий этап продукта»).

## Архитектура

Платформа состоит из нескольких AI-модулей.

**Модуль проверки качества** — определяет достаточность качества изображения, наличие шумов, размытость, артефакты, ошибки сканирования.

**Модуль сегментации** — использует современные архитектуры компьютерного зрения для выделения анатомических структур глаза.

**Модуль диагностики** — на основе результатов сегментации определяет наличие заболеваний и рассчитывает вероятность каждого диагноза.

**Генератор медицинских заключений** — использует языковую модель для формирования структурированного текста заключения на русском языке.

**Модуль аналитики** — собирает статистику исследований, оценивает качество работы модели и отслеживает изменения ее эффективности.

## Безопасность

OCTera разрабатывается с учетом требований медицинских информационных систем. Предусмотрены:

- шифрование данных;
- разграничение прав доступа;
- журналирование действий пользователей;
- анонимизация персональных данных;
- защищенная передача информации;
- резервное копирование;
- аудит безопасности.

## Бизнес-модель

Планируется несколько вариантов использования продукта.

- **Self-service подписка** (ближайший этап) — физлицо регистрируется само и платит подписку за доступ к анализу собственных снимков, по аналогии с ChatGPT/Claude.
- **SaaS** — клиника оплачивает подписку и получает доступ к облачной платформе.
- **Enterprise** — развертывание системы на инфраструктуре медицинской организации.
- **API** — оплата за количество выполненных исследований через API.
- **Research** — лицензии для университетов и научных организаций.

## Долгосрочная цель

Создать универсальную AI-платформу для офтальмологии, которая станет стандартом автоматического анализа ОКТ-исследований, поможет врачам принимать более точные решения, сократит время диагностики и повысит доступность качественной медицинской помощи.
